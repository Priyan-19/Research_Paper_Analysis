# 1. Executive Summary

The **LLM + Knowledge Graph Research Assistant** is an AI-powered research platform designed to help students, researchers, and academics analyze collections of research papers.

The system accepts research PDFs, extracts and understands their content, creates semantic embeddings, extracts research entities and relationships, builds a Knowledge Graph, and provides grounded research assistance through a combination of **Vector Retrieval + Knowledge Graph Retrieval + LLM generation**.

The system is designed to solve a limitation of conventional PDF chatbots and basic RAG systems: they can retrieve semantically similar text, but they do not explicitly model the relationships among papers, authors, concepts, methods, models, datasets, and citations.

The proposed system therefore maintains two complementary representations:

1. **Vector representation** for semantic document retrieval.
2. **Graph representation** for explicit entity and relationship retrieval.

These are combined through a **Hybrid Retrieval** pipeline before the final answer is generated by an LLM.

The platform will support:

- Research PDF ingestion
- Automatic paper metadata extraction
- Text extraction and chunking
- Semantic embeddings
- RAG-based question answering
- Knowledge Graph construction
- Graph-based retrieval
- Hybrid Vector + Graph Retrieval
- Grounded summaries
- Citation recommendation
- Research similarity / duplicate detection
- Research trend analysis
- Knowledge Graph visualization
- Evidence-backed answers
- Evaluation of retrieval and answer quality
- Optional advanced Graph Neural Network experimentation

# 3. Problem Statement

## 3.1 General Problem

Researchers and students often need to analyze large collections of research papers during literature reviews, project planning, thesis preparation, and research-gap identification.

Manually reading and connecting dozens or hundreds of papers is time-consuming and makes it difficult to consistently identify:

- Important concepts
- Research methods
- Models and algorithms
- Datasets
- Relationships between concepts
- Similar or overlapping research
- Relevant citations
- Research trends
- Connections between papers
- Potential research gaps

Existing keyword search systems are primarily lexical, while conventional RAG systems primarily retrieve semantically similar document chunks.

Although LLM-based PDF assistants improve document interaction, they can still suffer from:

- Hallucinated answers
- Weak relationship reasoning
- Missing multi-hop connections
- Poor citation grounding
- Difficulty identifying concept relationships across papers
- Limited research trend understanding

## 3.2 Formal Problem Statement

> Existing research-paper assistance systems do not sufficiently combine semantic document retrieval with explicit relationship reasoning across research entities. This project proposes a hybrid LLM-based research assistant that integrates Retrieval-Augmented Generation with a Knowledge Graph to improve research-paper understanding, evidence-grounded question answering, citation recommendation, research similarity detection, and research trend analysis.

# 5. Existing Approach: Vector Search / Basic RAG

Typical workflow:

```text
PDF
 ↓
Text Extraction
 ↓
Chunking
 ↓
Embeddings
 ↓
Vector Database
 ↓
Similarity Search
 ↓
Relevant Chunks
 ↓
LLM
 ↓
Answer
```

### Advantages

- Semantic retrieval
- Better than keyword search for natural-language queries
- Can ground LLM answers in uploaded documents
- Easy to extend

### Limitations

Basic RAG primarily answers:

> "Which pieces of text are semantically similar to this question?"

It does not naturally represent:

```text
Paper A → cites → Paper B

Paper A → uses → BERT

BERT → type of → Transformer

Transformer → used for → NLP

Paper B → improves → Method X
```

Therefore, graph relationships and multi-hop reasoning may be underused.

# 7. Product Goals

## Primary Goals

1. Allow users to upload research papers.
2. Extract and process paper content automatically.
3. Create semantic representations of paper chunks.
4. Build a research Knowledge Graph.
5. Support semantic Vector Retrieval.
6. Support Graph Retrieval.
7. Combine both into Hybrid Retrieval.
8. Generate evidence-grounded answers.
9. Provide source references for answers.
10. Recommend relevant citations.
11. Detect highly similar research papers.
12. Analyze research trends.
13. Visualize relationships between papers and concepts.
14. Provide measurable evaluation of system quality.

## Secondary Goals

- Support multiple LLM providers.
- Support background paper processing.
- Provide modular architecture.
- Make the system extensible for future GNN research.
- Provide a clean research-oriented UI.

# 8. Non-Goals for Initial MVP

The following should not be required for the first working release:

- Training a foundation LLM from scratch
- Building a custom vector database
- Building a custom graph database
- Full academic plagiarism detection
- Automatic publication submission
- Automated peer review
- Guaranteed factual correctness
- Fully autonomous research generation
- Advanced GNN-based reasoning in MVP
- Real-time crawling of the entire internet

# 12. F3. Semantic Embeddings

Each chunk is converted to an embedding.

```text
Text
 ↓
Embedding Model
 ↓
Vector
```

Example:

```text
"Transformer models are used in NLP"
                 ↓
[0.23, 0.81, -0.12, ...]
```

Embeddings are stored in PostgreSQL using pgvector.

# 18. F9. Grounded Answer Generation

The LLM receives:

- User question
- Relevant document chunks
- Graph evidence
- Paper metadata
- Citation information

The LLM should answer only using the available evidence whenever the question concerns the uploaded research corpus.

If evidence is insufficient:

> "The available papers do not provide enough evidence to answer this confidently."

# 48. Security Requirements

The system must:

- Never expose API keys
- Store secrets in environment variables
- Validate uploaded files
- Restrict file types
- Limit file size
- Sanitize extracted content where necessary
- Avoid executing uploaded files
- Implement authentication for production
- Apply authorization to user papers
- Log security-relevant failures

# 49. Performance Requirements

Target requirements for MVP:

- Upload API should respond quickly after creating a processing job.
- Heavy PDF processing should run asynchronously.
- Retrieval should normally complete within a few seconds depending on LLM latency.
- Vector retrieval should use indexed similarity search.
- Neo4j queries should be bounded and optimized.
- Large documents should be processed in batches.

Exact latency targets should be benchmarked rather than assumed.

---

# 50. Reliability Requirements

The system should gracefully handle:

- Invalid PDFs
- Scanned PDFs with no text layer
- Empty documents
- Large documents
- LLM API failures
- Rate limits
- Neo4j connection failures
- PostgreSQL failures
- Invalid structured LLM outputs
- Duplicate uploads

Every processing job should have a status:

```text
PENDING
PROCESSING
COMPLETED
FAILED
```

# 59. Most Important Development Principle

**Do not build this as one giant application.**

Build it as:

```text
PDF Module
    ↓
Embedding Module
    ↓
RAG Module
    ↓
Knowledge Graph Module
    ↓
Hybrid Retrieval Module
    ↓
Research Intelligence Module
    ↓
Evaluation Module
    ↓
Production Module
```

Each module must work independently before moving to the next one.

That way, if the final Hybrid RAG system fails, you can identify whether the problem is:

```text
PDF extraction
       OR
Chunking
       OR
Embedding
       OR
Vector retrieval
       OR
Graph extraction
       OR
Graph retrieval
       OR
Reranking
       OR
LLM generation
```

This modular approach is critical for both **software development and academic evaluation**.
